# Mech Arena Discord Bot

ARCHΛNGLE is an unofficial Mech Arena community helper for weapon and mech reviews, build lookups, reminders, calculations, and upcoming event updates. It is not affiliated with Plarium.

**Profile description draft (Discord Developer Portal):**

ECR event information is separate from promo codes; contact the relevant person for bot, database, or event questions.

## Commands and replies

- `/help`, `/invite`, `/weapon`, `/mech`, `/upgrade_cost`, `/builds`, `/recent`, `/upcoming`, `/ecr`, `/promo_codes`, `/timezone`, `/remind`, `/reminders`, `/cancel`, `/note`, `/calc`.
- Assigned database workers also use `/worker_setup`, `/worker_time`, `/worker_status`, `/worker_snooze`, and `/worker_pause`.
- Only Discord IDs **1442058583129722986** and **1444891876376186901** can start `/ping_loop` and `/dm_loop` or use `/stop_user_loops` to stop another member’s loops. These commands work in any server where the bot is installed; `/stop_loop` remains available for users to stop their own loops.
- Public message replies ping only the reply author. Other user, role, `@everyone`, and `@here` mentions are disabled.
- User-facing answers are kept concise and within Discord's 2,000-character limit. Exact catalog lookups and verified upgrade costs are resolved locally instead of waiting on AI; unsupported game questions abstain without an AI round trip.
- `/upgrade_cost` keeps rank-up resources separate from the A-Coins needed to buy missing Blueprints. Its optional `blueprints_owned` parameter defaults to zero; the purchase estimate uses the pinned calculator's per-rarity schedule and is not a live shop offer.
- Natural phrasing is supported for features such as `latest ECR event`, `latest promo code`, `what is 240 plus 60?`, `how much to upgrade Redox from rank 4 to 5?`, `best Surge build for 5v5`, `any builds for Redox?`, and fully specified reminders. ECR event questions and promo-code lookups are separate: a bare `ECR` asks about Event Crate Rush updates, while `/promo_codes` and explicit code requests search labeled codes only. A mech-specific build lookup asks for the requester’s SP value or range if it was not included, filters up to 100 public submissions by overlap with their recorded SP ranges, and returns concise summaries of every match (weapons, SP range, label, and note). Explicit game-mode hints also filter the matches. A request for a build without a mech asks which mech; explicit recent/list requests remain a recent unranked feed. The public feed has no ratings or votes, so community tags are not a verified meta ranking. The natural-language flow accepts the SP in the follow-up; `/builds` accepts an optional `sp_range`.

## Bounded ping loops

`/ping_loop`, `/dm_loop`, and `/stop_user_loops` are global guild commands, available wherever the bot is installed. Their runtime allowlist remains IDs `1442058583129722986` and `1444891876376186901`; unauthorized interactions are rejected. To also hide these commands from ordinary members in the picker, a server manager must configure them **in each server** under **Server Settings → Integrations → ARCHΛNGLE → Commands**: deny each command to `@everyone`, then allow the two operator user accounts. A bot token cannot apply these per-user settings. **Picker visibility is not guaranteed until each server manager saves and verifies the overrides.** Discord administrators can override command permissions, so runtime ID checks remain essential and reject non-operator admins.

- `/ping_loop member interval_seconds duration_seconds reason` sends one immediate channel message and then new follow-up messages, explicitly mentioning only the target member. The bot needs View Channel and Send Messages; the target must be able to view the channel.
- `/dm_loop member interval_seconds duration_seconds reason` sends an initial DM followed by separate DM messages. If the target cannot receive the initial DM, the loop does not start.
- `/stop_loop [member]` stops the caller's channel and DM loops; an operator may select another user. `/stop_user_loops member` is restricted to the two operators and also cancels both modes for that target. There is no `/emergency_*` command or `stop emergency` text handler; use `/stop_loop` to stop a loop.
- Safety bounds are a minimum **5-second interval**, maximum **30-minute duration**, and maximum **300 repeated pings**. A 5-second interval can run for at most 25 minutes to stay within the repeat cap. Each command invocation creates an independent loop pool, and multiple loops may run for the same target and mode. A target can have at most three active pools across both channel and DM destinations. Delivery failures, cancellation, process restart, and the deadline stop loops; they are not resumed after restart. One in-flight message may still arrive after a stop request.

## Nine database workers

`data/workers.json` contains the nine fixed Discord IDs and their assigned mech groups; Voidghost is S tier and Biform is excluded. The configured worker server is `1509560571563868160`, with task channel `1526008373009715313`.

1. A server manager with Manage Roles runs `/worker_setup` in the configured server. The bot creates `bot database workers` only if that role is missing, assigns it to the nine configured members it can find, and posts the initial time request. It reports missing members and assignment failures privately. Re-running can post another prompt. Duplicate same-named roles, elevated permissions, role hierarchy, and mentionability issues require server-side correction.
2. Each worker sets a daily time and IANA timezone with `/worker_time` or by replying to the prompt (for example, `8pm Asia/Kolkata`). The timezone is required initially. Changes update the daily schedule; `/worker_snooze` adds a one-time reminder without changing it; `/worker_pause` pauses the daily reminder.
3. Daily and snoozed reminders are attempted by DM and in the linked task channel. Failures at one destination do not prevent the other attempt. A worker who leaves the configured server has their daily schedule paused. DST gaps are skipped; ambiguous times use the earlier occurrence.

## Announcement ingestion and upcoming events

The bot is configured to read only the three user-specified announcement channels:

- `1524319795791659080` in server `1509560571563868160`
- `1512089401193271539` in server `1456726444603473922`
- `1570083896823906364` in server `1479464891709526051`

The background reader retries every 10 minutes. On its first successful access, it backfills the last 100 messages from each configured channel, then fetches new posts and refreshes a short tail for edits. A missing server, channel, or permission is transient: the bot keeps retrying and does not mark the source permanently unavailable. It stores only text, embed titles/descriptions/fields, channel labels, timestamps, and the Discord source link in the private `mech_bot_app.announcements` table. It never follows links embedded in the posts. `/ecr` and bare ECR/event questions show saved Event Crate Rush event posts only; `/promo_codes` and explicit promo-code questions search for clearly labeled codes separately. Code replies link to their source post and report a code as expired only when the post explicitly says so. Other codes are unverified for validity, and the bot does not send proactive promo notifications or claim a code works.

Announcement ingestion is enabled by default in the code; set `ANNOUNCEMENT_INGESTION_ENABLED=false` only to disable it. An existing deployment with that variable explicitly set to `false` must change it to `true`. Enable the privileged **Message Content Intent** in the Discord Developer Portal and grant the bot View Channel and Read Message History in each source channel. On first successful access it reads the newest 100 messages from each channel; then it fetches new posts every 10 minutes and refreshes a short tail for edits. Set `MESSAGE_CONTENT_ENABLED=true` separately if users should be able to ask natural-language questions without mentioning the bot. The bot ignores messages aimed at another member and reply chains to other members, never pings the author for an ambient answer, and rate-limits to one ambient answer per user/channel every eight seconds. Explicitly worded and fully specified natural reminder text is allowed; reminders and confirmations are private by DM, while notes and loop-management actions are not executed from ambient channel text. Unclear reminder requests are ignored in ambient chat. DMs and explicit bot mentions work with the intent off for the ambient feature. `ANNOUNCEMENT_CHANNEL_IDS`, if explicitly set, overrides the defaults and must include every channel to be read. The defaults include the two requested here (`1524319795791659080` and `1570083896823906364`) plus the previously requested `1512089401193271539`. `/upcoming` and a mention such as `@bot what’s coming up?` show future dates only when a post explicitly includes a year. Recent event-related posts with incomplete dates are labelled as such and are not claimed to be upcoming. Every result links to its source message; no date or event detail is invented.

## Payout reporting

- Polls the public `https://portico-hq-live.netlify.app/api/mech-arena/public/payouts` endpoint about once per minute. It reads public aggregate data only and monitors valid Discord IDs returned by the API, not just the nine workers.
- When an observed count first reaches 10 builds, or increases later that payout day, the bot DMs **1442058583129722986** with the user ID, day, and total. No payment is executed. Counts dropping and then returning to an already-reported high are not re-reported.
- Persisted high-water marks suppress ordinary repeats across restarts. A crash after Discord accepts a DM but before storage confirms it can still result in a duplicate. If the bot or site is down for a full payout day, the current API may not allow that missed day to be recovered.

## AI, privacy, and latency

- Optional AI uses an OpenAI-compatible `/chat/completions` endpoint configured by `AI_BASE_URL`, `AI_API_KEY`, and `AI_MODEL`. With private Supabase memory enabled, it may also receive up to five recent user/assistant turns scoped to the same user and exact channel or DM. Only the same user’s DMs, explicit bot mentions, direct replies to the bot, and (when `MESSAGE_CONTENT_ENABLED=true`) apparent questions in the exact channel are eligible; other participants’ messages, slash commands, private notes, and reminder data are excluded. Ambient questions are not answered from or written into any other member’s conversation history. Turns are capped at 1,500 characters per side and physically deleted after five hours. No API key should be posted or logged.
- Local exact-name lookups, rank-upgrade prices, and questions without matching confirmed game evidence skip the AI call. Other AI calls reuse a short-lived session and time out after 10 seconds, then fall back to confirmed local facts or an abstention.
- The bot uses one Railway worker instance. Reminders, worker schedules, payout high-water marks, and announcement records use the private Supabase schema; ping loops are in-memory and stop on process restart.

## Currency emojis

On startup, the bot tries to create or reuse three application-owned emojis from the transparent 128×128 assets in `data/emoji_*.png`. The registered names are versioned (`archangle_a_coins_v2`, `archangle_credits_v2`, and `archangle_blueprints_v2`) so refreshed artwork is created instead of silently reusing older `v1` images. `/upgrade_cost` uses the custom emoji codes for A-Coins, Credits, and Blueprints; if registration is unavailable, the reply attaches the same PNG assets. The optimized transparent PNGs are the runtime assets; the original checkerboard-backed references remain separate from the deploy files.

## Supabase and deployment

1. Production storage uses the private `mech_bot_app` schema and a least-privilege `mech_bot_runtime` PostgreSQL login with TLS. Existing Supabase project data is separate and was not wiped or imported. Additive migrations `add_mech_bot_announcements` and `add_short_lived_conversation_memory` have been applied to the `hq bot` Supabase project. The runtime role has only the required table privileges and still has no schema `CREATE` privilege. The checked-in `migrations/` SQL files are the repeatable local records of those changes. Keep `AUTO_MIGRATE=false` for the runtime account.
2. Deploy this project as a separate Railway **worker** with the `Procfile` command `python -m mechbot.bot`. Configure `DISCORD_TOKEN`, `DATABASE_URL`, `DATABASE_SSL=require`, and `PORTICO_BASE_URL` as Railway variables/secrets. Optional AI settings belong in the Railway service configuration; never paste secrets into chat or GitHub.
3. Bot role hierarchy matters for `/worker_setup`: its highest role must be above `bot database workers`. The worker command remains limited to the configured worker server. The bounded-loop commands are global guild commands and work in any server; configure their per-user visibility overrides separately in each server as described above. `/stop_loop` and other public commands also remain globally available, with guild mirrors for faster availability.
4. SQLite local fallback is for development only; an ephemeral Railway filesystem is not durable. Test live Discord delivery and PostgreSQL permissions separately from the local mock-based test suite.

## Game archive and coverage audit

`data/mech_bot_staging.sqlite3.gz` is the read-only offline catalog. Startup copies it to a private runtime path; it never edits the source archive. It now contains 150 source documents, 1,951 structured rows, 151 document versions, 904 flattened entities, 353 public-asset references, 432 image-OCR records, 36 existing image-transcription candidates, and the 251-screenshot weapon dataset with 22,652 candidate cells. The 84 screenshots from `PILOT.zip` and `MA SS.zip`, plus six earlier chat uploads, have raw OCR and confidence/bounding-box records staged; 72 pilot-bonus rows and 451 mech-stat rows are positional OCR candidates. The 90 raw OCR records from the 84 Drive images and six chat uploads are now marked verified and available to bot retrieval under the user-approved manifest. This does not independently validate OCR accuracy, screenshot identity, game version/date, or the user-attributed Gladitor label. The 523 derived pilot/mech stat-candidate rows remain `needs_review` and are not available as verified stats. The review workbook and detailed review artifacts are kept in the local workspace and are not included in the public repository. Drive data is labeled `Gladitor` at the user’s request; that attribution has not been independently verified. The packaged bot archive and the local source staging database passed SQLite integrity checks and retained the existing public-data fingerprint during this import. The importer now records one dynamic ISO-8601 UTC batch timestamp in document, OCR, and ingest-queue audit fields and metadata instead of assigning a hard-coded midnight. The original source ZIPs, review workbook, candidate/approval files, generated overlay reports, and SQL batch payloads are local review artifacts and are excluded from this public repository; the read-only runtime catalog snapshot is included.

All 52 Mech Arena Database documents, 59 captured Plarium forum original posts, and 36 upgrade-calculator documents are present. Their user-confirmed review is pinned to the existing snapshot; new or changed imports stay pending. The 12 existing public structured collections are searchable when their pinned source documents are verified, and verified non-code public documents/posts are eligible for archive retrieval. Only the two raw OCR collections (`drive_screenshot_ocr`, 84 rows; `user_upload_screenshot_ocr`, six rows) are searchable under the explicit user approval. Chat-upload excerpts are restricted to relevant game text; conversation messages, usernames, and image-generation prompts are not returned. The two derived pilot/mech candidate collections (523 rows) remain unsearchable until separately reviewed. Gladitor remains user-attributed, not independently verified. Public scripts, calculator client-source maps, and sitemaps remain stored for audit but are not fed into answer context as factual prose.

The separate user-confirmed screenshot values are exposed only when weapon identity is accepted. Cropped or unresolved identities/cells remain gated; `Sm` means 5 m, Arc Torrent 8 is excluded, Dreadshot 8 and 10 remain separate, and the Dreadshot 10 calculator energy mismatch is not silently used. The 342 earlier public-image OCR records remain `needs_review`; the 90 new Drive/chat raw OCR records are `verified` by the user’s direction, with OCR accuracy not independently rechecked and text clearly labeled as screenshot-derived. The 36 existing transcriptions remain `needs_independent_review`; all 523 derived pilot/mech rows remain unverified candidates. Those transcriptions and derived candidates are preserved for review but cannot be used as confirmed answer facts. Original image binaries and the two Drive ZIPs remain separate workspace files; they are not embedded in the bot catalog.

Captured scope is not equivalent to complete coverage of every public web/forum item: the forum snapshot contains original posts only (no replies and limited category-page sampling); some calculator media URLs were missing/rate-limited; and older/hidden site pages or future updates may not be captured. The bot must not claim those absences mean there is no information. `/weapon` and `/mech` provide concise reviews, key stats, perks, and listed purchase prices; purchase price is kept separate from upgrade cost. Calculator rank-only steps use the confirmed max-level-to-next-rank transition. Variant mismatches are withheld rather than guessed.
